## 1. 目的と背景

気象庁防災情報XML（以下 JMA XML）を取得してパースする PHP ライブラリを作り、OSS として Packagist で公開する。**[決定]**

2026-11-03 時点で、PHP 向けにメンテされている JMA XML ライブラリは存在しない（Packagist・GitHub を調査済み）。Rust（ciscorn/jmaxml）、.NET（oruponu/JmaXml）、Python（PixelNest256/jmaxml）、Go（p2pquake）にはある。

最終的な用途は、**地震を検知して安否確認を送る簡易システム** の構築。**[決定]** 安否確認システム自体はこの設計の対象外で、ライブラリの最初の利用者として別プロジェクトで作る。**[決定]** ライブラリは地震に限らず汎用に作るが、優先順位と品質の基準はこの用途で決める。

### 想定する利用の流れ（安否確認システム側）

1. 地震発生から約1〜2分後に「震度速報（VXSE51）」が届く。震度3以上の地域が **細分区域** 単位で分かる。
2. 続いて「震源・震度に関する情報（VXSE53）」が届く。**市町村・震度観測点** 単位で分かる。
3. 登録者の地域で、設定した震度（例：5弱）以上なら安否確認を送る。同じ地震では1回だけ送る。
4. 取消電文が来たら、取消を知らせる。

## 2. ゴール・非ゴール・アンチゴール

### ゴール（v0.1）

- JMA XML の全電文について、管理部（Control）、ヘッダ部（Head）、内容部（Body：気象・地震・火山）を型付きの PHP オブジェクトとして読める。
- 公開 Atom フィードを、行儀よく（条件付きGET、無駄な再取得なし）ポーリングできる。
- 地震の電文（VXSE51/52/53）を「1つの地震イベント」にまとめ、「どの地域が何度だったか」「取り消されたか」を安全に判定できる。
- 地域コードの対応（市町村 → 細分区域 など）を引ける。

### 非ゴール（v0.1 ではやらない）

- 気象・火山・津波の使いやすい高水準 API（低水準の型で読むことはできる）
- XSD による検証、XML の書き出し、`xs:any`（`jmx_add`）の中身の解釈
- WebSub（PubSubHubbub）でのプッシュ受信
- 緊急地震速報。公開フィードでは配信されていないとみられる（直近7日分の長期フィードに出てこなかった。気象庁の公式な記述は未確認）。
- 有料配信（気象業務支援センター、DMDATA.JP 等）への対応
- Laravel 等のフレームワーク連携
- 安否確認システムそのもの

### アンチゴール（技術的に動いても失敗とみなすもの）

- **誤報**：「訓練」「試験」の電文や、取り消された地震で安否確認が飛ぶような API になっていること。安全側の既定値（通常電文のみ、取消を明示的に扱う）にする。
- **見逃しが黙って起きる**：フィードの取得が10分以上止まり、高頻度フィードから電文が消えたことに気づけない。抜けの可能性は必ず呼び出し側に分かる形で返す。
- **気象庁に迷惑をかける**：取得済み XML の再ダウンロード、過剰なポーリング。1日10GB超で IP 遮断される。
- **公式に見える**：気象庁の公式ソフトと誤解される名前や説明。README に非公式であることと出典表記を明記する。

## 3. 制約

- PHP `^8.4`、ライセンス MIT。**[判断]** 作者の既存ライブラリ（shimomo/boatrace-php）に合わせた。

## 5. 各パッケージの要件

### 5.1 `jmaxml/core`

**方式：XSD と辞書からコードを生成する。** **[判断]**

- 入力は公式の XSD 一式（8ファイル、jmx / jmx_ib / jmx_eb / jmx_eb_nullable / jmx_mete / jmx_seis / jmx_volc / jmx_add）と、辞書 xlsx（要素の日本語名と説明）。
- ジェネレーターは PHP で書き、リポジトリ内に置く（`bin/` か `tools/`）。生成したコードはコミットする。利用者はジェネレーターを実行しない。
- 生成するもの：
  - XSD の complexType ごとに `final readonly class`。辞書の名称と説明を PHPDoc に入れる。
  - XSD の型との対応：必須の要素は非 null、`minOccurs=0` は nullable、繰り返しは `list<T>`、simpleContent は `value` プロパティと属性プロパティ、`xs:dateTime` は `DateTimeImmutable`、`xs:duration` は `DateInterval`、`jmx_eb:nullablefloat` と `nullableinteger` は `?float` と `?int`。
  - 各クラスの「DOM 要素から自分を組み立てる」コード（実行時リフレクションは使わない）。
- 入口は `Report::fromString(string $xml)` と `Report::fromFile(string $path)`。`Body` は `Meteorology\Body` / `Seismology\Body` / `Volcanology\Body` のいずれかになり、名前空間 URI で判別する。
- 管理部とヘッダ部だけを読む軽い入口も用意する。フィードの振り分けや取消の判定で、Body を読まずに済むようにする。

**読み込みの規則（寛容に読む）** **[判断]** oruponu/JmaXml の方針に倣う。

- 未知の要素・属性は無視する。将来の要素追加で壊れないようにするため。
- 子要素の順序は検査しない。
- 必須の要素が無い、値を型に変換できない場合は、XPath 風のパスを含む例外（`JmaXml\Exception\ParseException`）を投げる。
- `xs:token` 相当の値と数値は、前後の空白を除いてから変換する。実データには `<MaxInt>4 </MaxInt>` のように末尾に空白がある。
- 空要素は、文字列なら空文字列、nullable な数値なら null。実データには `<Serial></Serial>` がある。
- 数値の `NaN` は null にし、`description` などの属性はそのまま保持する。仕様上、`NaN` は演算してはいけない値のため。**[判断]**
- `xsi:nil="true"` は nillable な要素（`Head/TargetDateTime`）だけ null にする。
- 座標（`Coordinate` / `Line` / `Polygon`）は、元の文字列を保持したうえで、緯度・経度・高さに分解した値も取れるようにする。分解は ISO6709 の汎用パーサーに頼らず、要素の `type` 属性で度表記か度分表記かを判定する（一部電文は先頭の0を省くため）。
- 時刻は、電文に書かれたタイムゾーンを保持する。Control の `DateTime` だけが UTC で、他は JST。

**合格基準**：公式サンプル電文（2026-09-17 版、XML 546ファイル・126種類のデータ種類コード）が、すべて例外なく読めること。

### 5.2 `jmaxml/feed`

- 対象フィードは 4種類（`regular` / `extra` / `eqvol` / `other`）× 2系統（高頻度、長期 `_l`）。URL は `https://www.data.jma.go.jp/developer/xml/feed/{name}.xml`。
  - 高頻度：毎分更新、直近10分以上を掲載
  - 長期：毎時更新、約7日分を掲載（2026-11-03 実測。`extra_l` は約3MB・5,000件、`regular_l` は約4.6MB・9,500件）
- 取得は条件付きGET（`If-None-Match` / `If-Modified-Since`）。サーバーは S3 + CloudFront で `ETag`、`Last-Modified`、`Cache-Control: max-age=60` を返す。
- 新着の判定：エントリのリンク（電文 XML の URL）で、既に処理したかを判定する。気象庁のフィードでは `id` も同じ URL だが、ダウンロードする URL と既読のキーをそろえるためにリンクを使う。処理済みの記録は利用者が永続化できるよう、インターフェース（`StateStore`）にする。メモリ実装を同梱する。
- データ種類コードによる絞り込み：電文 URL のファイル名は `{yyyymmddhhmmss}_{n}_{データ種類コード}_{官署コード}.xml`（例：`20261103054436_0_VXSE53_010000.xml`）。ダウンロードする前にここで絞り込み、帯域を節約する。
- 抜けの検知：前回の取得成功から、高頻度フィードの掲載範囲を超える時間が経っていたら「抜けの可能性あり」を返す。利用者が長期フィードで追いつけるようにする（長期フィードでの追いつきを API として提供する）。
- 運用種別：既定では `Status` が「通常」の電文だけを返す。「訓練」「試験」は明示的に指定したときだけ返す。判定は Control 部で行うので、XML のダウンロードとヘッダ部の読み込みが必要になる。
- ポーリングの間隔は呼び出し側が決める（ライブラリはループやスケジューラーを持たない）。**[判断]** README で「60秒以上の間隔」を推奨する。
- `User-Agent` は設定可能にし、既定値にはライブラリ名とバージョンを入れる。

### 5.3 `jmaxml/codes`

- 気象庁の「個別コード表」（2026-10-19 版、xlsx 15ファイル）から、PHP の配列ファイルを生成して同梱する。v0.1 で必要なもの：
  - `地震火山関連コード表.xlsx` のうち、地震情報／都道府県等、地震情報／細分区域、気象・地震・火山情報／市町村等、震度観測点（この4つは1枚のシートで階層として対応している）、震央地名、津波予報区
  - 対応関係：市町村 → 細分区域 → 都道府県、震度観測点 → 市町村
- 安否確認で重要な理由：最初に届く震度速報（VXSE51）は細分区域単位でしか震度を出さない。登録者を市町村で持つなら、市町村 → 細分区域の対応が必要になる。
- 市町村コードは JIS X0402 の5桁に2桁を足した7桁（例：千代田区 `1310100`）。
- ジェネレーターは xlsx を読む（開発時の依存として phpoffice/phpspreadsheet 等を使ってよい）。xlsx のセルにはふりがな（`<rPh>`）が混ざっているので、本文だけを取り出すこと。
- コード表の版（気象庁のファイル日付）を、パッケージから参照できるようにする。

### 5.4 `jmaxml/earthquake`（当初の案は `jmaxml/seismology`）

名前は 2026-11-04 に変更した。core の生成クラスが `JmaXml\Seismology\`（地震の内容部）を使っているため、取り違えを避ける。

安否確認システムが直接使う層。

- 震度を表す enum（`1`、`2`、`3`、`4`、`5-`、`5+`、`6-`、`6+`、`7`）。大小比較ができる（「5弱以上か」）。XSD 上は `MaxInt` も `Int` もただの文字列なので、ここで解釈する。
- 「震度５弱以上未入電」の扱い：VXSE53 では、震度5弱以上と推定されるのに観測値が届いていない市町村・観測点が `<Condition>震度５弱以上未入電</Condition>`（観測点は `<Int>震度５弱以上未入電</Int>`）で示される。ヘッダ部にも `<Kind><Name>震度５弱以上未入電</Name></Kind>` として現れる。**震度不明として捨てず、「5弱以上の可能性あり」として判定できる** ようにする。安否確認では送る側に倒すべき値。
- 地震イベントへの集約：同じ地震の VXSE51 / VXSE52 / VXSE53 は同じ `EventID` を持つ。仕様上、一連の情報の単位は「Control/Title + Control/EditorialOffice + Control/Status + Head/EventID」で、その中で最新のものが有効。
  - イベントは「最大震度」「地域ごとの最大震度（都道府県・細分区域・市町村・観測点）」「震源・マグニチュード」「最終更新時刻」「取り消されたか」を持つ。
  - `InfoType` が「訂正」なら、その単位の最新電文を置き換える。「取消」なら、その単位の情報を取り消す。取消電文は Body に `<Text>` しか持たない。
  - 実装では、情報の単位を「Status + EventID + Control/Title」にした（2026-11-04）。同じ地震でも電文の種類によって EditorialOffice が違うため、地震のまとめには EditorialOffice を使わない。同じ種類の電文は同じ官署から出る前提
  - `Serial` は連番・一意の保証がない（仕様に明記）ので、順序の判定には使わない。順序は `Head/ReportDateTime` と `Control/DateTime` で決める。
- **EventID が別の地震はまとめない。** **[決定]**
  - 小さな地震 A が本震 B の揺れで発表基準に達すると、A と B に別々の EventID で震度速報が出る。A には震源の情報も取消も来ず、震度速報だけで終わる。公式サンプルの `32-35_04_*` と `32-35_08_*` がこの例。
  - ライブラリは EventID ごとに別のイベントとして扱い、時間や地域が近くても1つにまとめない。前震と本震を誤ってまとめ、強い本震を見逃す事故を避けるため。
  - イベントには段階を持たせる：「震度速報のみ（震源情報なし）」「震源あり」「震源・震度あり」「取消」。A は「震度速報のみ」のまま残る。
  - 関連しそうなイベントは「関連の可能性あり」として返す。条件の例：発生時刻が近く、震度3以上の細分区域が重なる。返すだけで、まとめるかどうかは利用者（安否確認アプリ）が決める。判定の時間幅などの具体的な条件は実装者に任せる。
- 判定 API の例：「この地震で、指定した市町村コードの集合のうち、震度 X 以上（未入電を含む）だったものはどれか」。VXSE51 しか届いていない段階では、細分区域から市町村に展開して判定する（codes を使う）。
- イベントの状態の永続化は利用者側に任せる。イベントは電文の列から再構築できる純粋なオブジェクトにする。**[判断]**
- 津波（VTSE41）は v0.1 の対象外。core で読むことはできる。

## 6. 仕様上の要点（実装者向けメモ）

- 電文は Control / Head / Body の3部構成。Head はすべての電文で共通の構造で、「いつ・何が・どこに」を持つ。緊急時などは Body を持たない電文もある。
- 名前空間：
  - `jmx` = `http://xml.kishou.go.jp/jmaxml1/`
  - `jmx_ib` = `.../informationBasis1/`
  - `jmx_eb` = `.../elementBasis1/`
  - `jmx_add` = `.../addition1/`
  - `jmx_mete` / `jmx_seis` / `jmx_volc` = `.../body/{meteorology1,seismology1,volcanology1}/`
- XSD はすべての電文種別をまとめて受け付ける作りで緩い。電文ごとにどの要素が出るかは「解説資料」PDF にしか書かれていない。生成した型はほぼすべて nullable になることを受け入れ、使いやすさは earthquake 層で補う。
- 2026-05-29 に新しい防災気象情報が始まり、気象警報の新しい電文（VPWW55〜61、VPWS50、VPWP50、VPBS50、VPZJ51 等）が加わった。旧電文（VPWW50/53/54、VXWW50、VPOA50 等）は令和10年度（FY2028）に廃止予定。XSD は共通なので、core は新旧どちらも追加の作業なしで読める。
- 公開フィードはリアルタイムのサポートがなく、予告なく止まることがある（気象庁 FAQ）。README の注意書きに入れる。

## 7. テスト方針

- core：公式サンプル電文 546件をすべて読み込むテスト。代表的な電文（VXSE51、VXSE53、取消の VXSE53、VTSE41、VPWW55、VPFD51）は、主要な値まで確認する。
- feed：HTTP はモック（PSR-18）。実際のフィードの形をフィクスチャとして保存してテストする。304応答、抜けの検知、運用種別のフィルタ、データ種類コードによる絞り込みを確認する。
- codes：生成した配列の件数と、既知の対応（例：千代田区 → 東京都23区の細分区域）を確認する。
- earthquake：公式サンプルの一連の電文を順に流し込み、集約結果を確認する。
  - `32-35_08_*` と `32-35_04_*` は地震が2つの例。期待値はイベント2件で、地震 A は「震度速報のみ」、地震 B は「震源・震度あり」。A と B は「関連の可能性あり」として結び付く。
  - 取消（`32-35_06_02` の VXSE52、`32-35_06_06` の VXSE53）、訂正、未入電（`32-35_06_04_240613_VXSE53`）、訓練電文の除外も確認する。
- 実際の気象庁サーバーに接続するテストは CI では既定で実行しない（手動か定期実行のみ）。
